# Plan: Signed OTA Update Mechanism (P4.3)

Rolle: Umsetzungsplan (Detaildokument, Skelett)
Grundlage: `../CRA_Compliance_Checklist.md`
Maßnahme: P4.3
CRA-Bezug: Annex I, Teil I, 1.9 (Pflicht-Nr. 7), Annex I, Teil II, Nr. 2 und 3 (Pflicht-Nr. 13 und 15)
Datum: 2026-09-28
Hinweis: Skelett. Abschnitt 2 ist verifiziert, die Abschnitte 3 bis 6 sind zu füllen.

## 1. Objective

Provide a way to deliver security updates that is authentic (signature checked), reproducible and
cannot be abused to install manipulated firmware. If no remote update path is provided, document
that decision and its consequences.

## 2. Current State (verified 2026-09-28)

- The firmware contains no OTA code: no `ArduinoOTA`, no `Update.h`, no `esp_ota` usage in `src/`.
- Flashing is local and physical: PlatformIO with `upload_protocol = esptool` and
  `board_upload.before_reset = usb_reset`; the filesystem goes separately through
  `upload_filesystem.bat`.
- Partition layout is `default_16MB.csv`; no dual application banks are configured.
- Consequence: updates require physical access today, which is safe but does not scale and does not
  yet satisfy Annex I 1.9 for a product that is expected to receive security updates in the field.

## 3. Design (TODO)

- First decide whether remote updates are in scope. If not, record the reasoning and how security
  fixes reach the field instead.
- If in scope: dual bank partition table, upload through the `Update` library, signature
  verification with mbedTLS (Ed25519 or ECDSA), manifest with version and hash, rollback through
  `esp_ota_mark_app_valid_cancel_rollback`, and an update endpoint protected by the authenticated
  session (P1.1) and the CSRF token (P1.2).
- Keep the USB path as the recovery route and document it.
